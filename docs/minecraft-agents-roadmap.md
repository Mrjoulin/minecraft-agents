# Minecraft Agents — пошаговый план повышения автономности

**Цель:** научить Worker самостоятельно ориентироваться в незнакомом Minecraft-мире, находить ресурсы, выполнять цепочки действий и восстанавливаться после ошибок.  
**Основа:** текущий проект [Mrjoulin/minecraft-agents](https://github.com/Mrjoulin/minecraft-agents) и практики из [3ndetz/unionclef](https://github.com/3ndetz/unionclef).  
**Порядок:** сначала сделать одного Worker компетентным, затем масштабировать эту компетентность на команду.

---

## Принципы реализации

1. **Не переписывать проект целиком.** Сохранить Node.js, Mineflayer и текущий runtime. Сначала расширить и проверить существующие возможности.
2. **LLM принимает решения, игровой runtime исполняет механику.** Модель выбирает цель и навык; код отвечает за физику, pathfinding, взаимодействие с блоками, таймауты и проверку результата.
3. **Действия должны быть композиционными.** Вместо одного сценария `collect logs` предоставить универсальные примитивы, из которых Worker сможет собирать более сложные задачи.
4. **Каждое улучшение подтверждать игровым тестом.** Unit-тесты полезны, но не заменяют прогоны на настоящем Minecraft-сервере.
5. **Не начинать с новых личностей, VLM или большего числа агентов.** Сначала устранить ограничения восприятия, навигации и навыков.

Главный практический ориентир из UnionClef — паттерн **`see → go → act`**: получить состояние мира, проверить/запустить перемещение, дождаться результата, выполнить действие и проверить изменение мира. В UnionClef для внешнего агента предусмотрены отдельные perception/movement/action-инструменты и статус длительных операций. Это стоит перенести как принцип, не копируя весь Java/Fabric-стек.

Ссылки: [UnionClef README](https://github.com/3ndetz/unionclef), [AGENTS.md](https://github.com/3ndetz/unionclef/blob/main/AGENTS.md), [Agent Py4J levers](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md), [MCP server](https://github.com/3ndetz/unionclef/blob/main/docs/features/MCP_SERVER.md).

# План работ

## Шаг 0. Зафиксировать baseline и сделать воспроизводимый benchmark

**Зачем:** без исходных измерений нельзя понять, помогла ли новая карта, навигация или Skill System. Один успешный демонстрационный прогон не показывает устойчивость.

**Что сделать**

- Добавить несколько фиксированных сценариев на отдельном тестовом Minecraft-мире.
- Для каждого сценария задавать seed/состояние мира, начальную позицию, инвентарь и цель.
- Писать в JSONL: наблюдение, выбранное действие, аргументы, начало/конец операции, причину ошибки, изменение инвентаря и координаты.
- Собирать базовые метрики: выполнение цели, время, пройденное расстояние, число застреваний, число повторных попыток, расход LLM.
- Прогонять каждый сценарий несколько раз, а не оценивать по одному запуску.

**Минимальные сценарии**

1. Найти дерево, добыть 8 брёвен и вернуться к базе.
2. Найти ресурс за препятствием (вода, перепад высоты или плотная растительность).
3. Получить недостижимую цель, обнаружить ошибку и выбрать другую.
4. Построить небольшую секцию по заданным координатам.

**Готово, когда:** есть baseline-отчёт с результатами нескольких повторов; последующие версии можно сравнивать с ним автоматически.

**Где менять:** `scripts/`, `test/`, логирование текущих агентов.  
**Ориентиры:** [текущий репозиторий](https://github.com/Mrjoulin/minecraft-agents), [PR #3](https://github.com/Mrjoulin/minecraft-agents/pull/3).

## Шаг 1. Дать Worker полноценное структурированное наблюдение

**Зачем:** сейчас LLM получает слишком сжатый текстовый контекст и не имеет удобного способа запросить нужные сведения о ближайшем пространстве. При этом Mineflayer уже знает координаты, блоки, сущности и состояние инвентаря.

**Что сделать**

Добавить единый метод `get_observation()` с ограниченным, структурированным ответом:

```json
{
  "self": {
    "position": {"x": 120.5, "y": 71, "z": -35.2},
    "yaw": 90,
    "pitch": 0,
    "health": 20,
    "food": 18,
    "onGround": true
  },
  "environment": {
    "dimension": "overworld",
    "timeOfDay": 6000,
    "weather": "clear"
  },
  "nearby": {
    "blocksOfInterest": [],
    "entities": [],
    "containers": [],
    "hazards": []
  },
  "inventory": [],
  "navigation": {
    "isMoving": false,
    "target": null,
    "stuck": false
  }
}
```

Дополнительно реализовать небольшие запросы, чтобы не отправлять модели весь объём данных сразу:

- `scan_area(center, radius, filters)` — обзор выбранной области;
- `find_blocks(blockTypes, center, radius, limit)` — кандидаты на ресурс;
- `inspect_block(position)` — подробности об одном блоке;
- `get_entities(radius, types)` — ближайшие сущности;
- `get_inventory()` — предметы, свободные слоты и экипировка;
- `get_environment()` — измерение, время, погода и опасности.

Каждая пространственная запись должна содержать координаты. Различать «неизвестно» и «проверено, но пусто». В ответ включать только релевантные объекты и ограничивать размер результата.

**Готово, когда:** Worker может запросить окружение и корректно ответить, где он находится, какие ресурсы/препятствия видит и что находится вокруг целевой точки. Проверить на нескольких разных начальных позициях.

**Где менять:** `src/skills.js`, `src/agents/worker.js`; при необходимости вынести perception в отдельный модуль.  
**Референс:** [UnionClef: perception tools и getGameState/getBlocksAround](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md).

## Шаг 2. Сделать навигацию отдельной управляемой операцией

**Зачем:** перемещение не должно быть скрытой частью одного большого сценария добычи. Агенту нужно понимать, куда он идёт, сколько осталось, почему путь не найден и можно ли отменить движение.

**Что сделать**

Ввести API длительной операции:

- `start_navigation(target)` → возвращает `operationId`;
- `get_operation_status(operationId)` → `running/success/partial/failed/timeout/cancelled`;
- `cancel_operation(operationId)` → останавливает текущую операцию;
- `can_reach(target)` → предварительная проверка достижимости и причины отказа.

В статусе операции возвращать:

- текущую позицию и целевую позицию;
- расстояние до цели;
- время с начала операции;
- текущую фазу (поиск пути / движение / ожидание / восстановление);
- stuck-флаг и причину ошибки;
- число попыток.

Добавить ограниченное восстановление: проверить цель повторно, перестроить маршрут, выбрать соседнюю достижимую точку или вернуть понятную ошибку Worker. Не допускать бесконечных retry.

Сохранить текущий Mineflayer Pathfinder на этом этапе. Не переносить Tungsten из UnionClef, пока benchmark не покажет, что текущий pathfinder — основное ограничение.

**Готово, когда:** бот стабильно достигает доступных целей; для недостижимых возвращается диагностируемый отказ; при застревании операция завершается или восстанавливается, а не зависает.

**Проверки:** открытая местность, лес, склон, вода, препятствие, недостижимая точка, отмена движения. Измерять success rate, время и фактическую длину маршрута.

**Где менять:** `src/skills.js`, навигационные функции Mineflayer; обработку операций — в отдельном executor-модуле.  
**Референсы:** [UnionClef Agent levers: gotoXYZ/pathStatus/stopPathing/canReach](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md), [mineflayer-pathfinder](https://github.com/PrismarineJS/mineflayer-pathfinder).

## Шаг 3. Разделить поиск ресурса, перемещение и добычу

**Зачем:** текущий сценарий `collect` слишком тесно связывает поиск, выбор цели, навигацию и сбор. Это затрудняет понимание ошибок и ограничивает повторное использование кода.

**Что сделать**

Реализовать три независимых инструмента:

1. `find_resource(type, searchArea)` — найти и вернуть список кандидатов с координатами, расстоянием и типом.
2. `navigate_to(position)` — добраться до конкретного кандидата, используя Шаг 2.
3. `mine_block(position, toolPolicy)` — проверить блок и инструмент, добыть блок и проверить фактическое изменение инвентаря/мира.

После этого собрать поверх них универсальный `gather_resource(type, amount)`:

1. проверить инвентарь и свободное место;
2. найти подходящий источник;
3. выбрать доступную цель;
4. переместиться к ней;
5. добыть ресурс;
6. проверить результат;
7. повторить, пока не достигнуто нужное количество или не исчерпаны варианты;
8. вернуть `success`, `partial` или `failed` с объяснением.

Убрать из базового механизма жёсткую привязку к брёвнам и направлениям света. Тип ресурса должен быть параметром, а не отдельным сценарием.

**Готово, когда:** один и тот же `gather_resource` умеет добывать минимум несколько типов блоков, а ошибки поиска, доступа и добычи различаются в логах и ответах.

**Где менять:** `src/skills.js`; старые действия Worker перевести на новый механизм, сохранив совместимость на время миграции.  
**Референсы:** [UnionClef: `mineBlock`, `getBlocksAround`, `canBreakBlock`](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md), [mineflayer-collectblock](https://github.com/PrismarineJS/mineflayer-collectblock).

## Шаг 4. Добавить Spatial Memory и исследование неизвестной территории

**Зачем:** локальный поиск каждый раз начинает почти с нуля. Агенту нужна память о том, где он уже был, что там обнаружил и какие маршруты оказались непроходимыми.

**Что сделать**

Начать не с тяжёлой полной voxel-карты, а с карты секторов и точек интереса (POI):

- известные ресурсные кластеры и их приблизительное количество;
- сундуки, база, ориентиры, вода, опасные участки;
- посещённые и ещё не исследованные сектора;
- неудачные маршруты/недостижимые позиции;
- время последнего наблюдения и уверенность в записи.

Хранить записи в координатах мира. Устаревающие данные помечать как stale: блок мог быть добыт, а путь — изменён. Не считать отсутствие записи доказательством отсутствия ресурса.

Добавить `explore_area()`:

1. определить границу между известной и неизвестной территорией;
2. выбрать ближайшую безопасную точку на этой границе;
3. проверить достижимость;
4. переместиться туда;
5. просканировать область;
6. обновить карту и индекс ресурсов;
7. выбрать следующую точку либо завершить исследование.

Это вариант frontier-based exploration. На первом этапе выбор frontier можно сделать алгоритмическим; LLM не должна выбирать каждый блок или каждый шаг движения.

Для мультиагентности хранить личную карту каждого Worker отдельно. Общими делать только те сведения, которыми агенты действительно обменялись.

**Готово, когда:** Worker на незнакомой карте исследует новые сектора, запоминает найденные ресурсы, не посещает бесконечно одни и те же места и может вернуться к ранее обнаруженному кластеру.

**Проверки:** лес с разреженными деревьями, лес с несколькими кластерами, ресурсный кластер уже вырублен, маршрут к известной точке перекрыт.

**Где менять:** новый модуль `src/world/` или `src/memory/`; вызывать его из perception/skills.  
**Референсы:** [UnionClef: perception levers](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md), [Mineflayer](https://github.com/PrismarineJS/mineflayer).

## Шаг 5. Ввести Skill Registry с единым контрактом

**Зачем:** когда появятся новые действия, нельзя продолжать добавлять их как несвязанные ветки в Worker. Агенту нужен понятный каталог навыков и единый способ получать результат.

**Что сделать**

Для каждого skill описать:

- название и назначение;
- JSON Schema входных параметров;
- предусловия;
- ожидаемые эффекты;
- возможные статусы и ошибки;
- таймаут и возможность отмены;
- проверку фактического результата.

Начальный набор примитивов:

- `scan_area`, `find_blocks`, `inspect_block`;
- `navigate_to`, `navigation_status`, `stop_navigation`;
- `mine_block`, `place_block`;
- `craft_item`, `equip_item`, `consume_item`;
- `interact_with_block`, `interact_with_entity`;
- `inspect_inventory`, `transfer_items`.

Над примитивами реализовать составные навыки:

- `gather_resource(resource, amount)`;
- `return_to_base()`;
- `deposit_resources()`;
- `obtain_item(item, amount)`;
- `build_structure(specification)`.

Все навыки должны возвращать один формат результата:

```json
{
  "status": "partial",
  "skill": "gather_resource",
  "requested": 12,
  "completed": 7,
  "reason": "resource_depleted",
  "position": {"x": 120, "y": 71, "z": -35},
  "recoveryHints": ["find_resource", "explore_area"]
}
```

LLM должна видеть описание и схему доступного skill, но не должна самостоятельно исполнять низкоуровневую механику.

**Готово, когда:** Worker может вызвать навык по схеме, получает проверяемый результат, а новый skill можно добавить без переписывания основного цикла Worker.

**Где менять:** `src/skills.js`, новый `src/skills/registry.js` (или аналогичная структура), `src/agents/worker.js`.  
**Референсы:** [UnionClef MCP server](https://github.com/3ndetz/unionclef/blob/main/docs/features/MCP_SERVER.md), [UnionClef Agent levers](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md).

## Шаг 6. Добавить иерархическое планирование целей

**Зачем:** автономность появляется, когда агент получает цель, а не пошаговую инструкцию. Он должен уметь определить необходимые подзадачи, их зависимости и критерии завершения.

**Что сделать**

Ввести Goal/Task Planner. Цель превращается в дерево или DAG подзадач. У каждой задачи должны быть:

- входные параметры;
- предусловия;
- зависимости от других задач;
- нужные ресурсы;
- критерий завершения;
- статус и результат;
- варианты восстановления.

Пример:

```text
BuildShelter
├── SelectBuildSite
├── EnsureResources
│   ├── Obtain(wood, 40)
│   ├── Obtain(cobblestone, 20)
│   └── Obtain(torch, 4)
├── PrepareSite
├── BuildFoundation
├── BuildWalls
├── BuildRoof
└── VerifyShelter
```

Начать с 2–3 целей, которые можно проверить автоматически: `gather_resource`, `craft_item`, `build_shelter`. Не пытаться сразу поддержать любые формулировки и все игровые механики.

Использовать LLM для декомпозиции неоднозначных целей и выбора стратегии. Проверку предусловий, учёт рецептов, статусы подзадач и выполнение известных последовательностей оставить детерминированному коду.

**Готово, когда:** Worker получает, например, «получи железную кирку» и сам строит последовательность получения материалов, крафта и экипировки; после отказа может перестроить план.

**Где менять:** `src/agents/worker.js`, новый `src/planner/`; для общекомандных целей — позднее `src/agents/commander.js`.  
**Референсы:** [UnionClef](https://github.com/3ndetz/unionclef) (иерархия игровых задач), [AutoClef usage](https://github.com/3ndetz/autoclef/blob/1.21/usage.md) (команды уровня цели `@get`, `@food`, `@equip`; архивный проект, использовать как пример интерфейса, а не текущей реализации).

## Шаг 7. Добавить систематическое восстановление и перепланирование

**Зачем:** хороший агент не обязан успешно выполнять каждую попытку. Он должен понимать, что именно пошло не так, и выбирать другой способ.

**Что сделать**

Свести ошибки к ограниченному набору причин:

- `target_not_found`;
- `target_unreachable`;
- `resource_depleted`;
- `missing_tool`;
- `inventory_full`;
- `path_stuck`;
- `danger_detected`;
- `interaction_failed`;
- `timeout`.

Для каждого skill определить recovery policy. Например:

- `target_unreachable` → проверить соседние точки подхода или выбрать другой ресурсный объект;
- `resource_depleted` → обновить Spatial Memory и выполнить поиск заново;
- `missing_tool` → вызвать `obtain_item(tool)`;
- `inventory_full` → вернуться на базу и освободить инвентарь;
- `path_stuck` → остановить операцию, обновить наблюдение и пересчитать маршрут.

Перепланировать только при значимом событии или после неудачи, а не на каждом игровом тике. После нескольких неудачных попыток возвращать задачу с понятным статусом, не зацикливаться.

**Готово, когда:** в тестах с заблокированным маршрутом, вырубленным лесом и полным инвентарём Worker либо завершает задачу альтернативным способом, либо корректно сообщает, почему это невозможно.

**Где менять:** Skill Executor, `src/agents/worker.js`, Planner.  
**Референс:** [UnionClef Agent levers](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md) — раздельные операции движения/действия и проверка состояния.

## Шаг 8. Только после автономного Worker — координация нескольких агентов

**Зачем:** если Worker не умеет самостоятельно искать ресурс и выполнять задачу, увеличение количества агентов только умножит ошибки и дублирование работы.

**Что сделать**

Ввести общий Task Board с полями:

- `taskId`, цель и параметры;
- исполнитель и срок аренды задачи;
- статус `pending/accepted/running/blocked/completed/failed`;
- целевая область/ресурс;
- прогресс и последний heartbeat;
- причина блокировки и результат.

Добавить:

- подтверждение принятия поручения;
- отчёт о прогрессе и завершении;
- временное резервирование секторов и ресурсных кластеров;
- возврат зависших задач в пул;
- выбор Worker с учётом расстояния, инвентаря, навыков и занятости;
- запрет дублирования уже зарезервированных целей.

Commander должен выдавать структурированную задачу, а не только текстовую инструкцию. При этом текущие механики proximity speech и скрытых мотивов сохранить отдельным слоем — они не должны управлять надёжностью исполнения задачи.

**Готово, когда:** 2–3 Worker одновременно собирают разные ресурсы, не идут к одной цели без необходимости, отчитываются о прогрессе и передают задачу при сбое.

**Где менять:** `src/agents/commander.js`, новый `src/coordination/task-board.js`, Worker event loop.  
**Референс:** [UnionClef MCP / Py4J interface](https://github.com/3ndetz/unionclef/blob/main/docs/features/MCP_SERVER.md) — единый интерфейс управления игровым телом.

## Шаг 9. Долговременная память и обучение на опыте

**Зачем:** после появления устойчивых наблюдений и навыков можно использовать историю, чтобы не повторять ошибки и лучше выбирать стратегии.

**Что сделать**

Разделить память на:

- **Working memory:** текущее задание, активная операция, ближайшее окружение.
- **Spatial memory:** сектора, ресурсы, ориентиры, опасности, посещённые маршруты.
- **Episodic memory:** задача → решение → действия → результат → причина неудачи.
- **Semantic memory:** рецепты, требования к инструментам, свойства блоков, проверенные способы получения ресурсов.
- **Social memory:** действия других агентов и подтверждённые факты о взаимодействиях.

Сохранять в эпизодах не только текст размышления, но и объективные игровые события: координаты, вызванный skill, аргументы, изменение инвентаря и мира, outcome.

На основе истории считать успешность навыков и стратегий. Не давать модели автоматически считать любое собственное рассуждение фактом: воспоминания должны опираться на наблюдаемые результаты и иметь временную метку.

**Готово, когда:** после перезапуска Worker помнит известные ресурсные точки, не повторяет заведомо неудачный маршрут и может опираться на прошлый успешный способ решения похожей задачи.

**Где менять:** новый `src/memory/`, интеграция с Spatial Memory, Skill Registry и Worker.  
**Референс:** [UnionClef Agent levers](https://github.com/3ndetz/unionclef/blob/main/docs/features/AGENT_PY4J_LEVERS.md) — пример отделения фактического игрового состояния от решений когнитивного агента.

# Метрики качества

Метрики собирать с первого шага и сравнивать по одинаковым сценариям/seed.

| Область | Метрика | Что показывает |
|---|---|---|
| Навигация | Path Success Rate | Доля целей, которых бот достиг |
| Навигация | Path Efficiency | Кратчайший путь / фактический путь |
| Навигация | Stuck Time | Время, проведённое в застревании |
| Навигация | Recovery Rate | Доля ошибок, после которых бот восстановился |
| Восприятие | Observation Accuracy | Совпадение наблюдений с реальным состоянием мира |
| Исследование | New Area Coverage | Сколько новых секторов исследовано |
| Исследование | Resource Discovery Yield | Найденные ресурсы на единицу времени/расстояния |
| Навыки | Skill Success Rate | Успешность каждого навыка |
| Навыки | Partial Completion Rate | Частота частичного выполнения |
| Планирование | Goal Completion Rate | Доля достигнутых конечных целей |
| Планирование | Replan Success Rate | Успех после сбоя первоначального плана |
| Команда | Duplicate Work | Доля дублирующихся действий |
| Команда | Idle Ratio | Время без полезной активности |

**Основные показатели на ранних этапах:** Path Success Rate, Recovery Rate, Resource Discovery Yield и Goal Completion Rate. Они непосредственно показывают, стал ли агент лучше ориентироваться и выполнять задачи.

# Итоговый acceptance test

Считать базовый уровень автономности достигнутым, когда один Worker на новой карте без заранее заданных координат способен:

1. Осмотреть окружение и определить своё положение.
2. Самостоятельно найти ресурсный участок.
3. Выбрать достижимую цель и построить маршрут.
4. Добыть заданное количество ресурсов.
5. Обнаружить истощение участка или препятствие и сменить цель/маршрут.
6. Вернуться на базу и передать ресурсы.
7. Сообщить Commander проверяемый результат.

После этого проверить то же задание на нескольких seed и с 2–3 Worker. Успех должен измеряться долей завершённых прогонов, временем и количеством вмешательств, а не одним удачным видео.

# Что пока не делать

- Не переписывать проект на Java/Fabric и не переносить Tungsten до объективного сравнения pathfinder.
- Не внедрять VLM как основной способ навигации: сначала использовать координаты, блоки и сущности из Mineflayer.
- Не просить LLM выбирать каждый шаг движения или анализировать полный voxel-массив.
- Не увеличивать количество агентов до появления устойчивого одиночного Worker.
- Не развивать в первую очередь личности, секретные мотивы и сложную Theory of Mind: эти механики не компенсируют неработающие навигацию и навыки.
